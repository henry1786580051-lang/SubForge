# 翻译修复安全性与任务生命周期审计

日期：2026-08-31

## 结论与范围

本轮是对现有生产路线的安全修复，不是候选翻译框架上线，也不是一次新的模型质量竞赛。

- 保留当前生产路线及单人、多人场景各自的复核选择策略。
- 移除仅凭个别英文关键词就重写整句、补充事实或删除尾词的兜底分支。
- 保留有局部证据的文本整理，但增加代词覆盖、说话人、源语言和显示间隔保护。
- 修复任务启动、取消、预览增量、恢复保存中的已复现问题。
- 不调用真实翻译 API，不下载模型，不修改用户字幕，不使用新的保留样本。
- 不更新应用版本号、不构建 `.app` 或安装包、不进行 GitHub 操作。

工作开始前已有大量未提交改动。本报告仅说明本轮新增修复，不能将当前相对 Git HEAD 的全部差异归因于本轮。

## 方法

1. 追踪实际生产调用路径，而非仅查看候选模块或提示词。
2. 构造可以在修复前失败的离线反例，核对错误是否来自实现，而非预期差异。
3. 优先删除不能可靠证明安全的自动改写，避免再为单条视频增加记忆式译文。
4. 保留正向测试，证明有效的词语修正、连接词整理、受校验的 LLM 修复路径仍可工作。
5. 使用已暴露的开发字幕直接探测相关辅助函数，记录文件哈希，不写回字幕。
6. 运行完整非集成回归、前端构建和静态检查。

## 已确认的问题与处理

### 1. 关键词触发的整句替换会破坏原意

主要位置：`subforge/core/translate/llm_translator.py` 中的 `_repair_high_confidence_semantic_asr_fallbacks`、`_deterministic_chinese_fluency_fallback`、`_deterministic_chinese_prose_fallback`。

已复现的风险包括：

- 看到 `stick the car in the car` 就替换成插入钥匙，忽略否定、玩具车或后续内容。
- 看到 `dine-in bits`、`up badge` 就补充特定改装品牌或车型徽章。
- 将 `I'm such a` 固定改成“说来惭愧”，即使后文是正面评价。
- 将 `I / think ...` 改成“说真的”，或者重复添加主语。
- 对备胎空间、阅读媒介、转向系统、比较句等使用预设整句，丢失数字、条件或反例。
- 将 `first/earliest video` 一律理解为首发视频。
- 给已经完整的“我的车是某年买的”再加“这是”，产生重复谓语。
- 清理 `short / walk`、`in the last / two years` 等边界时，直接删去长度、时间方向等信息。
- 将 `arrange this / like ...` 改成“重新布置这里”，凭空补充“重新”和地点。

处理方式：删除上述没有充分依据的确定性改写。复杂语义问题仍交给原有受校验的模型复核路径，不通过校验就保留此前内容。没有增加全篇思考调用。

这并不意味着原始译文中的所有问题会自动消失。删除危险兜底，是防止程序制造新的错误，不是以不改写代替语义评估。

### 2. 主语清理可能删掉上一句的宾语

主要位置：`_remove_stranded_chinese_subject_tails` 及原先重复存在的兜底代词移动分支。

反例：`They support us. We / need help.` 对应“他们支持我们 / 需要帮助”，旧兜底会变成“他们支持 / 我们需要帮助”。前一句的宾语因此消失。

修复：

- 删除第二条未经校验的代词搬移路径，只保留一处保守的重复主语清理。
- 要求相邻编号、明确的英文新句主语、下一条助动词、相同的下一条中文主语以及分隔开的中文尾词。
- 中文代词按长词优先匹配，避免把“我们”的“我”当成独立主语。
- 清理后仍须保留前文已有代词的覆盖数量，含英语代词变格及缩写；不能仅凭空格就删除宾语。
- 说话人切换、已知源语言切换、明显显示间隔均阻止确定性跨条移动。

代词覆盖计数是保守保护条件，不是完整的语义或指代证明。不确定的边界仍应进入语义复核。

### 3. 局部术语修正扩大到了无关实体

- 不再因为附近提到核电，就把工厂统一改成核电站。
- 仅在当前源句明确包含 nuclear plant、实体数量受限、没有制造业冲突证据、译文尚未正确出现核电实体时，尝试局部替换。
- Cobalt 修正要求当前源句明确提及 Cobalt，且没有 Cruze；译文已经包含 Cobalt 时，不再把同句的科鲁兹也替换掉。
- 限定适用的目标语言，避免向其他目标语言注入简体中文。

保留反例与正例，分别验证“汽车工厂不能被改成核电站”和“明确核电站误译为工厂仍可局部修正”。

### 4. 同一窗口中的后续整理可能覆盖前面的修改

确定性边界整理现在从窗口内最新结果读取文本，而不是继续使用最初快照。保留的连接词移动、音响修饰词移动和挡位去重均遵守这一约束。

挡位去重要求上一条已出现同一挡位，不能删除下一条不同挡位。音响修饰词只有确实从左侧移除时才向右侧添加，防止重复执行累加文字。

### 5. 第二轮局部复核异常会中止整个任务

主要位置：`LLMTranslator._finalize_translated_list`。

第一轮相邻字幕修复有异常保护，第二轮锁定重试却没有。服务在第二轮抛错时，整项翻译失败。

修复后，第二轮请求失败会记录警告并保留进入该修复前的结果，不提交第一轮已被拒绝的改写。正常重试成功后仍须通过原有校验。该行为与第一轮已有降级策略一致，不把未通过校验的候选当作成功修复。

### 6. 恢复流程重复整篇复核，并污染检查点

主要位置：`subforge/core/translate/base.py`。

此前完整候选恢复尝试失败后，发布恢复内容时会再次执行整篇 finalizer。即使第二次完成，任务仍按原失败路径退出。同时 finalizer 可能修改输入对象，导致第一次失败的中间结果污染原本可保留的译文。

修复后：

- 完整候选只执行一次整篇恢复检查。
- 在独立的字幕条目副本上尝试恢复；失败修改不污染已有检查点。
- 成功且通过原有验证才恢复为正常结果。
- 失败时仅发布此前可恢复内容，任务仍如实失败。

离线测试证明失败路径从两次整篇 finalizer 调用降为一次。正常成功流程不减少校验。真实 API token、总耗时和总体质量变化未在本轮测量，不能据此推算百分比收益。

### 7. 启动与取消请求存在交错竞态

主要位置：`frontend/src/lib/useTaskMonitor.ts`、`SubtitlePanel.tsx`、`WorkflowWorkspace.tsx`。

- 启动请求未返回时取消，晚到的任务 ID 原先仍会被附着到界面。
- 旧取消请求晚返回，可能清掉新的当前任务。
- 启动按钮和字幕编辑区的翻译入口此前没有统一经过同一套任务保护。
- 取消未被后端确认时，界面原先仍可能表现为已停止。

修复后使用启动/取消代次校验，拒绝重复启动；迟到的已创建任务会请求取消，而不是接管界面。取消失败时继续监控，并检查任务是否已经完成。已有完成通知不能被较晚的取消错误污染。

字幕编辑区的工具栏、快捷键和菜单共用同一个启动函数。未改动页面布局或翻译配置字段。

### 8. 预览乱序、缺帧与可变对象共享

后端 `TaskManager` 现在在锁内记录预览版本。若通知发出前已有更新，发送最新完整快照，不再给旧增量贴上新版本号。

前端 `mergeTaskPreview` 对 append/patch 要求版本连续、总条数一致、ID 不重复且可匹配。发现缺失增量时不推进版本，由已有轮询获取完整快照恢复。

同时修复：

- 字段删除无法用普通 patch 表达时，使用完整替换。
- 任务完成、失败、取消结果均保存独立快照，迟到的对象修改不能篡改终态。
- 完成或恢复文件的迟到读取不能覆盖用户已编辑的字幕。
- 旧 WebSocket 的关闭事件不能重连并替换新连接。

测试中的 WebSocket 已显式替换为本地假对象，不连接实际服务。

### 9. 取消或输出不可写时未保留翻译成果

主要位置：`backend/app/api/subtitle.py`、`backend/app/core/blocking.py`、`backend/app/core/task_manager.py`。

旧失败路径向同一不可写目录再次保存 recovery，仍失败后会删除临时检查点。用户主动取消时也没有保存已完成的译文。

新策略：

1. 有可用译文时，按原策略保存 recovery，保持中英顺序和中文标点处理。
2. 原位置不可写或无法解析时，尝试应用工作目录下的 `recovery/<task_id>/`，使用受限长度文件名，隔离任务。
3. 两个持久位置都不可写时，不删除已经存在的非空临时检查点，并在任务结果中提示其局限。
4. 保存成功后仅授权访问确切的生成文件，不扩大目录权限。
5. 状态仍是失败或取消，不伪装成完成。
6. 阻塞工作线程退出前，即使异步调用者被重复取消，也不能提前进入资源清理；取消任务的同文件互斥锁在工作线程结束后才释放。

这不是断电或强制终止下的完整持久化保证。运行中的临时检查点仍有保存间隔，临时目录仍可能被系统清理。取消后的成果会落盘，但本轮没有新增历史任务恢复界面，也不会把已取消任务的内容自动覆盖到用户新启动的任务中。

## 保留的边界与后续验收

- 本轮只证明已复现错误被阻止、已有离线功能测试通过，不证明完整翻译已达到信达雅。
- 没有运行真实 Windows 桌面程序；文件长度、阻塞取消和路径授权测试不能替代 Windows 安装包验证。
- 没有重新构建 `.app`。当前打包应用仍是本轮修改之前的构建。
- 没有测量真实 API token、缓存命中率或整篇翻译耗时。删除早期确定性兜底可能让原本命中的窗口进入模型复核，其净开销仍需授权后实测。
- 旧路线仍包含复杂的语义提示与检测规则。本轮没有宣布所有规则都可靠，也没有将候选规划器或候选输出路径设为生产默认。
- 后续加入自动改写，必须同时给出正例、否定/数量/主语/跨说话人反例、幂等性测试，以及跨主题样本证据；“某一个案例读起来更顺”不能单独作为接入依据。
- 真正需要复核的旧错误不能用“保留原文”宣告修复。后续端到端测试应同时统计新增错误、未解决旧错误、审计调用数和耗时，不能只看完成率。
